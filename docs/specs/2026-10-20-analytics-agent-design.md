# Bounded training analytics agent

Date: 2026-10-20. Status: implementation contract; capability spike complete, not a shipped feature.
Base: `f8eb62c7`. Scope: authenticated MCP `analyze({prompt})`, reusable Elixir context, independent experimental Jev review, offline comparison corpus. No UI, autonomous writes, kcal, new agent framework, or live benchmark claims.

## Capability decision and evidence

The owner approved a separate OS-isolated SQLite helper after the planner escalated the pinned dependency's gaps. Keep the Elixir controller and existing `Coach.Client`/ledger. Do not patch Exqlite or installed dependencies.

Pinned `mix.lock` Exqlite 0.42.0 is insufficient as the untrusted SQL boundary:

- `deps/exqlite/c_src/sqlite3_nif.c:1854` authorizer only checks an operation-code deny array; ignores function name/table arguments. Denying `:function` denies useful SUM/COUNT along with unsafe functions. Named policies are not supported.
- `:819` passes NULL for `sqlite3_prepare_v3`'s tail. `prepare("SELECT 1; ATTACH ...")` succeeds and executes only SELECT, rather than rejecting multiple statements.
- `lib/exqlite/sqlite3.ex` has no public `sqlite3_limit` or per-connection allocator cap. `shrink_memory` is not a cap. PRAGMA hard_heap_limit is SQLite-global, unsuitable for the application's shared NIF runtime.
- `c_src/sqlite3_nif.c:499, 2214` progress handler observes cancellation; cancel also interrupts and wakes busy waits. Probe confirms cancellation of an active recursive aggregate. This does not preempt arbitrary allocation/function execution or prove a hard deadline. Killing an Erlang caller is not cancellation of a dirty NIF.

Executable planning probes and full outputs live under `.docs/analytics-agent/`: `exqlite_capability_test.exs`, `sandbox_capability_test.py`, `exqlite-capability.log`, `sandbox-capability.log`. Existing focused MCP baseline: 57 passed. Probes establish feasibility, not production security certification. Task 1 must promote the relevant assertions into maintained tests and test its actual launcher/protocol.

## Approved runtime boundary

Use a small Python standard-library helper (`priv/analytics/sqlite_helper.py`), Linux bubblewrap, and Python >=3.11 / SQLite >=3.40 with `Connection.setlimit` and `set_authorizer`. No pip packages, SQL parser dependency, new NIF, shell interpolation, network client, or production database file. The installed proof used Python 3.14.8, SQLite 3.53.4. Record and check supported runtime versions at startup; pin OS image/package versions in deployment rather than claiming the Python SQLite engine is Exqlite's engine.

Each query starts a fresh helper from the *same immutable bounded snapshot*. It builds only `sessions` in `:memory:` using fixed DDL and bound inserts, commits, sets limits, then installs a default-deny authorizer before preparing model SQL. Helpers never receive credentials, user IDs, DB paths, or raw application/provider structs. A one-query process avoids connection reuse/cancel races. SQL errors cannot poison the next query.

Launch only an absolute configured executable and fixed argv, through `Port.open({:spawn_executable, ...})`, not a shell. The sandbox argv uses `--unshare-all --die-with-parent --new-session --cap-drop ALL`, read-only `/usr`, distribution-specific read-only library mounts/symlinks, isolated `/proc`, minimal `/dev`, a size-bounded private `/tmp`, only the helper script mounted read-only at `/helper.py`, `--clearenv`, and `/usr/bin/python3 -I /helper.py`. No home, application tree, database directory, secrets directory, host `/tmp`, host network, or inherited non-protocol descriptors. Validate executable/helper ownership and non-world-writability. `/usr` is a runtime mount: deployments must not place secrets there. Require Linux unprivileged namespaces and bubblewrap; never use `--not-a-security-boundary` or an unconfined fallback. Rootless container policies must explicitly permit the required namespaces.

Before accepting input, helper sets hard=soft `RLIMIT_AS=128 MiB`, `RLIMIT_CPU=1 second`, `RLIMIT_CORE=0`, `RLIMIT_NOFILE=32`, `RLIMIT_FSIZE=0`; verifies them. Disable temp files (`temp_store=MEMORY`), extension loading, and trusted schema before untrusted SQL. No model-controlled setup PRAGMA. Read a four-byte big-endian input length, reject >2 MiB, then read exactly that many JSON bytes; premature EOF is invalid. Do not wait for stdin EOF (BEAM ports cannot half-close stdin). The trusted guardian is the sole writer and sends exactly one frame; helper exits after its one response. Runtime code is trusted, SQL/data are not. RLIMIT_AS bounds virtual allocation for the helper (not BEAM RSS); it is not an application-wide memory guarantee. SQL is the threat model, not arbitrary Python code execution or a hostile kernel.

An Elixir guardian owns the port independently of the request process, monitors caller death, and enforces a 1,000 ms *whole-helper* deadline including startup/input/prepare/fetch. The absolute deadline is captured before the guardian call and its timer is installed before launch. Frame delivery uses bounded 4 KiB `Port.command/3` submissions with `:nosuspend`, yielding between chunks and retrying backpressure only within the same remaining deadline; cancellation writes are also nonblocking. A timed-out launcher with queued input may terminate its port with `:epipe`, which must release admission and finish the explicit timeout rather than waiting indefinitely for an exit-status message. BEAM Port cannot capture stderr separately: the approved trusted `helper_launcher.py` is spawned by absolute `/usr/bin/python3 -I`, with a cleared environment, and owns bwrap and its independent stdout/stderr pipes (8 KiB/1 KiB). It never executes SQL itself. On timeout/caller death, the guardian sends cancellation through the framed-input pipe; the launcher explicitly SIGKILLs the trusted bwrap OS PID and waits for exit before returning. A 100 ms guardian backstop SIGKILLs the launcher if cancellation stalls; bwrap's parent-death flag then kills its namespace. Cleanup adds scheduling/reaping latency, not extra SQL execution time. `Port.close` alone is not a kill proof. `--die-with-parent`/PID namespace kills the worker when bwrap/guardian dies; no untrusted child can spawn through allowed SQL. Test actual child cleanup via host PID/status monitoring, including caller death. No production execution until hard kill/reap is proved. Max two active helpers application-wide; admission returns `executor_busy`, no unbounded waiting queue.

Linux Erlang ports may be children of `erl_child_setup`, not directly of BEAM. The launcher registers `PR_SET_PDEATHSIG(SIGKILL)` against its actual OS parent, checks stable `/proc` identity/start time/executable before and after registration, and accepts only the claimed BEAM parent or its same-runtime `erl_child_setup` child. Executable ownership/non-writability and all ancestor directories are checked; unavailable/racy proc information refuses. Stdin EOF separately cancels an individual guardian's helper. Standalone service-identity preflight may launch the same Python supervisor directly; it verifies its immediate parent's stable identity. Tests use Linux pidfds to observe actual worker death, including caller/guardian/launcher/OS-parent death and parent loss before registration. These tests are not a security certification.

Startup health check runs the same sandbox with denied ATTACH/function/tail and rlimit probes; absent/failed controls disable analytics with `executor_unavailable`. Do not silently weaken the contract on another OS. A deployment must run this health check as the service identity; developer-machine success does not prove deployment feasibility.

### SQL enforcement

Use Python `Connection.execute(sql)` (never `executescript`). It prepares one statement and rejects non-comment trailing statements, including ones hidden by quoted semicolons/comments; NUL rejected explicitly. Empty/no-result statements are errors. Retain legal trailing comments. Verify this on supported CPython releases in regression tests, not regex splitting. Default deny every authorizer action except SELECT, READ of `main.sessions` approved columns (including SQLite's empty-column COUNT case), and the following lowercase named functions: `sum,count,avg,min,max,round,abs,coalesce,nullif`. Match function name from SQLITE_FUNCTION arg2, not arg1. No RECURSIVE, transaction, PRAGMA, ATTACH/DETACH, schema writes, temp objects, metadata tables, virtual/table-valued functions, extension loading, file functions, randomblob/zeroblob/printf, date/time functions, or unknown future action. Operators/CASE and ordinary SELECT subqueries/joins are available subject to bounds. No regex-only security or Jev permission override.

Set SQLite limits to SQL_LENGTH=4,096; LENGTH=65,536; COLUMN=16; EXPR_DEPTH=64; COMPOUND_SELECT=8; VDBE_OP=25,000; ATTACHED=0; VARIABLE_NUMBER=0; WORKER_THREADS=0. Verify effective values, failing closed if required controls unavailable. Data insertion happens before VARIABLE_NUMBER=0 and restrictive authorizer. Progress callback every 100 VM operations checks monotonic deadline; this is a fast cooperative stop, with OS kill as hard backstop. Fetch incrementally; never fetchall. Return at most 100 rows, 16 columns, 1,024 UTF-8 bytes per string/cell, 8 KiB encoded result. Exceeding a limit returns `result_too_large`, never a misleading partial aggregate or silently truncated evidence. Reject non-finite numeric output and duplicate column names; use array rows with explicit ordered columns. Bound stdout/stderr independently and kill on overflow; never log helper stderr verbatim.

Protocol v1: one length-prefixed bounded JSON object via stdin (no request EOF requirement): `{version:1, rows:[[...]], sql:"..."}`; column order is compiled into helper and `Schema.columns/0`, not model input. Response one JSON object then EOF: `{version:1, ok:true, columns:[...], rows:[[...]]}` or `{version:1, ok:false, code:"sql_denied|sql_error|result_too_large|query_timeout|invalid_input"}`. Elixir validates version, types, bounds, exit status, absence of trailing bytes; helper messages do not contain raw exception paths. Elixir adds evidence IDs/timing. Whole stdin <=2 MiB plus four-byte frame header, stdout <=8 KiB, stderr <=1 KiB. Any malformed output, crash, signal, sandbox failure, timeout, or unavailable resource control is an explicit error, not empty successful evidence.

## Snapshot and metric contract

`Analytics.Snapshot.build(%Scope{}, now: DateTime.t()) -> {:ok, %Snapshot{rows, as_of, timezone, schema_version:1}} | {:error, atom}`. Trusted `timeout:` may tighten the default 15,000 ms transaction checkout and query timeout; invalid/nonpositive timeouts refuse before database work. The analyst forwards its remaining allowance, with the independent run watchdog authoritative. Load in one read transaction from `WorkoutSession` with `user_id == scope.user.id`, completed_at <= fixed now, state completed, then require `AuthoritativeSession.authoritative?/1`. No model-supplied filters/user IDs. Read at most 5,001 candidates; >5,000 refuses with `snapshot_too_large`, never silently picks a biased recent subset. Strict projection excludes raw notes, memory, cadence, program/video JSON, workout names, free-form tags, credentials, and all other tables. Source validity may inspect snapshots in trusted Elixir but only the approved scalar projection crosses the boundary. Max encoded snapshot 1 MiB, max helper envelope 2 MiB; all queries reuse exactly those rows. Invalid timezone returns `invalid_timezone`, no UTC fallback.

One table `sessions`, columns in this exact order (SQLite types):

| Column | Type / definition |
| --- | --- |
| session_id | INTEGER, owned session id, evidence link only |
| completed_at | TEXT UTC ISO8601 |
| local_date | TEXT YYYY-MM-DD, `UserTime.local_date/2` using captured owner timezone |
| source_kind | TEXT plan/video/manual |
| burpee_type | TEXT six_count/navy_seal |
| capture_mode | TEXT tracked/timed/logged |
| reps_actual | INTEGER nullable, `burpee_count_actual` |
| reps_planned | INTEGER nullable, `burpee_count_planned` |
| duration_sec_actual | INTEGER nullable |
| duration_sec_planned | INTEGER nullable |
| credited_seconds | INTEGER, `History.credited_seconds/1`: max(actual duration or 0, 0) for authoritative non-warmup sessions; 0 otherwise |
| warmup | INTEGER 0/1; canonical `tags == "warmup"` convention, not generic substring matching |
| pace_sec | REAL nullable; actual duration / actual reps only if both positive |
| reps_per_20_min | INTEGER nullable; `round(actual reps / actual duration * 1200)` matching `Stats.Series.progress/1` |

Keep malformed/missing actuals as NULL, never substitute planned work into actual pace. A projected INTEGER outside signed int64 (including normalized throughput overflow after Stats.Series-compatible rounding) refuses the entire snapshot with `invalid_snapshot`; it is invalid analytics data, not insufficient history or an empty successful result. Completed sessions may count credited minutes differently from measured duration; document `History.credited_seconds/1` precisely in schema resource. Include warmups explicitly; prompts default to non-warmup comparisons and separate burpee types/capture methods. Normalized throughput is extrapolation, not a prescribed 20-minute PB or proof of comparable endurance. PB eligibility remains `AuthoritativeSession.prescribed_plan_pb_eligible?/1`; this schema does not expose sufficient fields to certify it. No causal inference from observational data. No universal meaning of “improved”: clarify whether volume, frequency, pace or comparable-session performance unless user supplied a definition. Local dates are computed before SQL, preserving DST behavior without SQLite timezone assumptions.

## Elixir interfaces and budgets

Modules under `BurpeeTrainer.Analytics`:

- `Schema.columns/0`, `Schema.text/0`, `Schema.version/0`; resource is `burpee://analytics/schema`, static and non-user-specific.
- `Executor.query(%Snapshot{}, sql, timeout_ms: <=1_000) -> {:ok, %{columns:[string], rows:[[scalar]], duration_ms:integer}} | {:error, code}`. Helper guardian/launcher implements the OS boundary above. Caller cannot supply a looser cap.
- `Analytics.analyze(%Scope{}, prompt, opts \\ []) -> {:ok, output_map} | {:error, %Workouts.Error{}}`. Trusted options include deterministic clock/recorded Req transport, `review_mode: :off | :shadow | :enforce`, `call_budget: %CallBudget{}` and nonnegative `call_allowance: integer`; the latter two tighten reservation admission for the serial evaluator as specified below. Omitted review_mode uses deployment configuration. MCP passes no options and cannot choose config, review mode, ledger IDs or limits.
- `Trace.fetch(%Scope{}, trace_id) -> {:ok, payload} | {:error, :not_found}`. No unscoped public lookup. `Output.validate(map, evidence_ids)` performs strict validation and existence checks, not semantic grading.

Limits are shared constants, not independently drifting prompt text: prompt 4,096 UTF-8 bytes, analytical intent 512 bytes, SQL 4,096 bytes, snapshot 5,000 rows / 1 MiB, queries 3 attempts including denied/error queries, analyst model calls 5, review model calls 3, combined ledger reservations 8, run wall deadline 45,000 ms, helper wall 1,000 ms, analyst HTTP timeout <=5,000 ms, review <=3,000 ms, each provider body <=existing Client 262,144 bytes. Cumulative accepted model text/context 64 KiB, per assembled final output 48 KiB (model narrative <=8 KiB). No next operation if remaining deadline cannot fit its bounded work and finalization; exhaustion produces budget_exhausted. Existing Client max output tokens stays unchanged; oversized content is rejected before it enters trace/context. A receive_timeout alone is NOT an end-to-end bound.

### End-to-end deadline producer seam (Task 2)

Task 2 explicitly owns narrow `Coach.Client` changes, `Coach.Client.Deadline` and `test/burpee_trainer/coach/client_deadline_test.exs`, plus analytics run supervision. Add optional trusted `deadline_ms` (absolute `System.monotonic_time(:millisecond)` value) to Client.chat/2 and decide/3. Analytics always supplies `min(run_deadline - finalization_reserve, now + role_timeout)` with a 1,000 ms finalization reserve; expired deadlines admit no transport. Existing non-analytics callers retain their interface/behavior. The absolute deadline may be tighter than config.timeout_ms's existing 1,000 ms lower bound; that lower bound must never extend deadline_ms. This is not merely passing config.timeout_ms: current Client only sets receive_timeout. Installed Req.Finch forwards pool_timeout/receive_timeout/request_timeout, while Finch documents request_timeout as HTTP/1-only and best-effort. Neither it nor socket connect timeout is the whole-call watchdog.

A supervised metering coordinator owns reservation and completion outside a monitored **transport-only** task running bounded encoding/Req/response parsing. Its absolute deadline starts before DNS/connect/pool acquisition, never resets on chunks, and limits the entire Req operation, not only time between packets. Coordinator waits only until deadline, then terminates/monitors the transport task and records provider_timeout (unknown billing when no valid usage arrived). Set explicit finite connection, pool, receive, and request timeouts no greater than remaining. Installed Req 0.7.5 rejects `:connect_options` together with any `:finch` option (`Req.Finch.finch_name_options/1`), so the parent-approved equivalent is sanitized `finch: [conn_opts: [timeout: remaining], pool_timeout: remaining, receive_timeout: remaining, request_timeout: remaining]`. Only trusted pool size/count survive inherited Finch options; no inherited named pool or TLS override survives. strip inherited conflicting Req/Finch options that could relax them. Retry/redirect remain disabled. The watchdog is authoritative across DNS, pool startup/acquisition, TLS/connect, slow chunked responses and parsing, regardless of protocol. Worker cancellation must release/cancel its Finch checkout/request; test resource reuse rather than assume caller death is cleanup. No unbounded shutdown wait or late success delivery. Killing the transport-only task is allowed; killing the ledger owner as a timeout mechanism is not.

On timeout/caller death, coordinator cancels transport and finishes the existing reservation exactly once with outcome timeout/cancelled and available validated usage; missing usage/cost stays NULL (unknown billing), retains reserved_cost_usd, and still consumes call/day/run caps. No refund or retry and no fabricated zero cost. Ledger completion uses bounded DB timeout; failure leaves the durable reservation counted, emits a safe explicit ledger-finalization failure for inspection, and does not label it completed or start another call. Coordinator must outlive analysis-worker cancellation long enough to attempt this bounded finalization. Preserve existing disabled-coach/provider gates and usage on invalid responses. No provider request or reservation may begin after the coordinator has accepted cancellation/deadline expiry.

`Analytics.analyze` has an independent monitored run-worker watchdog returning by the 45,000 ms deadline (subject to BEAM scheduling, not a real-time OS guarantee), covering snapshot/SQL/model/trace work, not just admission. Reserve the final 1,000 ms for bounded trace/finalization; database waits use remaining-derived timeouts. On run timeout return budget_exhausted without fabricated trace/evidence; if no trace was persisted return explicit run_timeout error instead of a fake trace_id. Stop the worker and notify any independent Client coordinator to cancel; coordinator ledger cleanup may finish after the caller's deadline but cannot launch another request. Test caller death and timeout races, no late successful response/reservation, and eventual durable counted timeout/unknown billing. This is a wall bound on the user operation, not a promise a remote provider ceased billing.

Task 2 red/green tests must use local real transport fixtures: delayed TLS connection handshake; a saturated one-connection Finch pool held by a synchronized request; and slow chunked responses whose individual chunks arrive within receive_timeout but total exceeds deadline. Assert elapsed deadline with documented scheduler tolerance, transport/checkout cleanup, final counted ledger outcome and unknown billing. Also cover blocking recorded adapter/parsing, caller death and shared run timeout. Immediate mocked timeout errors alone do not establish the bound. No paid calls.

### Tighten-only evaluator controls (Task 2 producer, Task 3 consumer)

Reuse Client.chat/2 and decide/3 with purposes analytics/analytics_review, preserving shared user/daily cost policy. Task 2 provides `Analytics.CallBudget` (`lib/burpee_trainer/analytics/call_budget.ex`, focused `call_budget_test.exs`) and scoped `Coach.Ledger.reservation_count(scope, run_id)` counting every reserved row, independent of outcome, including failed/timed-out/inflight calls. A count read failure is an error, never zero. The result is `{:ok, %{reservations: n, inflight: n}}` (or explicit error); CallBudget.usage adds remaining. New count reads use a finite 1,000 ms timeout. No additional persistence is required: existing ledger run_id/run_cap transaction is the admission boundary.

Frozen API:
- `CallBudget.new(scope, ceiling)` creates a trusted owner-bound struct with fresh ledger_run_id UUID and immutable nonnegative absolute reservation ceiling. It grants no coach permission or daily-policy override. Normal analyze creates a fresh ceiling-8 budget when none supplied.
- `CallBudget.usage(scope, budget) -> {:ok, %{reservations: n, remaining: max(ceiling-n,0)}} | {:error, error}` queries scoped durable reservations on both success and failure. A mismatched owner is rejected. Usage is not token count or successful-call count.
- `CallBudget.client_options(scope, budget, purpose, call_allowance: remaining) -> {:ok, keyword} | {:error, error}` reads starting count n and returns trusted ledger options with the budget's shared ledger_run_id and `budget: [run_cap: min(ceiling, n + min(8, remaining))]`. Reject invalid/negative allowance; allowance zero refuses without transport. Each analysis freezes this absolute cap once at entry and uses it unchanged for every internal analyst/reviewer/repair reservation. Never recompute n+allowance on every turn (that would replenish the allowance). Local 5/3/8 per-analysis counters remain mandatory even if the shared evaluation ceiling exceeds 8. Caller may not override daily caps/reservation costs. For a baseline Client call Task 3 uses this same producer helper with purpose analytics_baseline, never direct unmetered Req.

A serial evaluator creates one budget with CLI max-calls N for the entire comparison, not a fresh budget per arm. Before each case/arm it obtains usage, passes `call_allowance: remaining` and the same `call_budget`, plus trusted `review_mode: :off` for B / `:enforce` for C; A uses CallBudget.client_options for every baseline model exchange. After every outcome, including errors, it queries usage and subtracts actual reservations, not a guessed one call per analysis. Shared absolute ledger ceiling prevents overspend even if cancellation races with accounting or a stale count is supplied. If accounting/finalization is unavailable or reservations remain inflight, halt comparison until resolved; do not start the next arm with guessed allowance. Each analysis has its own trace UUID; traces record the shared ledger_run_id separately. No model or MCP option can construct/modify this trusted budget or select review_mode.

Task 2 must deliver a recorded multi-arm test with **one global call remaining**: the analyst's one response requests a query needing review/repair, but neither reviewer nor repair nor the next arm can obtain a second paid reservation. Assert durable reservation_count across failed/timed-out calls, both off/enforce mode selection, cap-zero no-call behavior, non-replenishment across turns, owner rejection, and unchanged daily/coach gates. Task 3 consumes these accepted seams without analyst/Client edits. No quality benchmark or paid calls are implied. Do not route through Coach.Agent or expose mutation tools.

## Bounded loop and typed output

Analyst response is a strict tagged JSON object with action `query`, `final`, or `clarify`. Query carries `interpretation`, `intent`, `sql`; interpretation <=1,024 bytes. Only one action/query per turn. Schema/definitions and fixed snapshot coverage accompany prompt. Ordinary `sql_error` may be repaired within the *same* global budgets; denied operations remain recorded and spend an attempt. No provider-controlled parallel tool execution. Each successful result gets code-generated `q1` etc.; failures have trace events but are not citable evidence. Clarification returns no speculative answer.

Final output (all keys required, additional keys rejected): `status` in answered/needs_clarification/insufficient_data/budget_exhausted, `interpretation` string, `answer` string, `findings` array of `{text, evidence_ids:[string]}`, `evidence` array of `{id, intent, sql, columns, rows}`, `limitations` array of strings, `trace_id` UUID. Max 8 findings/8 limitations, strings <=1,024 bytes, answer <=2,048 bytes; model narrative <=8 KiB and assembled output <=48 KiB. Code assembles evidence and trace_id; model cannot invent or rewrite results. Validate every cited ID exists and answered requires at least one successful evidence result and a citation. This is provenance checking, not proof the answer follows from the numbers. Non-answer statuses must not contain uncited numeric claims; deterministic budget/insufficient fallback explains reason. Explicit infrastructure/provider errors use `{:error, Error}` and MCP isError, not a fabricated answered/insufficient result. Snapshot-too-large is insufficient_data with a clear coverage limitation, not provider success.

## Independent Jev review

Config `analytics_review.mode = :off | :shadow | :enforce`; when review configured default shadow. Unconfigured review in shadow records `review_unavailable` and proceeds unreviewed; output limitation says so. Enforce with unavailable/failed/malformed reviewer fails with review_unavailable, never auto-approves. Off records disabled. Reviewer sees question, interpretation, metric definitions, SQL intent/proposal and preceding successful evidence, not raw provider envelopes, credentials or additional data. `decide/3` asks one typed judgment: proceed/revise_query/clarify_with_user and bounded reason. Use question key `query_review` with choices `proceed`, `revise_query`, `clarify_with_user`; consume `answers.query_review.choice` as the judgment. Existing Decisions responses may include confidence/probabilities (validate types and bound size), not an assumed free-text reasoning response. Request a second bounded typed question only if supported by the configured API; otherwise record a code-generated reason derived from choice, not fabricated provider rationale. Reject missing/wrong choices or unexpected question keys.

Shadow records each judgment/failure but never changes analyst messages, control flow, or final answer based on it. Enforce proceed executes; revise feeds reason back and spends model/review/query-proposal budgets; clarify returns needs_clarification. Maximum three reviewed proposals regardless of retries; no approval replaces SQL enforcement. Reviewer cost counts against same run/daily caps. Jev is experimental advisory reasoning, not a security boundary or guaranteed correctness improvement.

## Traces, privacy and failure behavior

Task 2 adds `analytics_traces` (UUID id, user_id FK, bounded JSON payload, expires_at, inserted_at; index user_id/expires_at). Store question, interpretation, schema version/as_of/timezone, SQL intent/query, compact successful results/error codes, reviewer judgments, call usage/timings, final status. No raw snapshots, notes, full prompts/provider payloads, auth headers, SQL exception stack traces or secrets in logs. Prompt itself is sensitive user data. Payload <=64 KiB; store evidence once and final output by evidence reference (do not duplicate query results). Reject overflow explicitly, never save a fake complete trace. Retain seven days and at most 20 traces per user, prune on scoped write/read; expired records inaccessible immediately and provide scheduled deletion via existing Oban pattern. Trace write failure returns trace_unavailable instead of an inspectability claim. Failed runs may retain bounded error traces without claiming final output success.

Access only through scope-checked `Trace.fetch` and a local operator-only `mix burpee_trainer.analytics.trace --user-id ID --trace-id UUID` (construct trusted Scope from operator-selected account; this is not model permission). CLI emits sensitive owner data to stdout only on explicit request, never globally lists traces. No trace UI or unauthenticated HTTP route. Owner deletion must cascade or delete trace rows; test it.
